# Инструкции для Claude Code в проекте на базе этого шаблона

Этот файл едет вместе с шаблоном в каждую новую копию. Следуй этому алгоритму
при разработке приложения в этой папке.

## Что это за проект

Полностью локальное Android/iOS-приложение (Expo). **Бэкенда нет и не будет** —
вся persistence в `expo-sqlite` на устройстве. Единственные системные
возможности за пределами экрана — локальные уведомления и вибрация, и то
только если конкретному приложению это нужно по смыслу. Никакой регистрации,
никакого обязательного интернета, никакой аналитики/рекламы/трекеров.

Privacy Policy, публикация в Google Play, Data Safety форма — **вне зоны
ответственности этого проекта**, этим занимается другой человек позже отдельно.
Не создавай PRIVACY.md и не трать на это время.

## Язык, нейминг, иконки, палитра — обязательные правила

- **Весь пользовательский интерфейс — на английском.** Тексты экранов, кнопки,
  плейсхолдеры, пустые состояния, название приложения, названия сущностей —
  всё по-английски. Код, комментарии и общение с пользователем — как обычно,
  по-русски. Только то, что видит пользователь внутри самого приложения,
  должно быть на английском.
- **В package name/bundle id не использовать имя, инициалы или ник
  разработчика.** Не `com.briver.<slug>` и подобное. Использовать нейтральную
  схему на основе имени приложения, как в прошлых проектах:
  `com.<slug>.app` (см. `co.habitiq.app`, `com.standy.app`,
  `com.stretchly.breaks` — паттерн `com.<slug>.<короткое-слово>` тоже ок).
- **Иконки в UI — только из `lucide-react-native`** (уже в зависимостях
  шаблона), не эмодзи и не сторонние SVG-наборы. Импорт по имени:
  `import { CheckCircle } from "lucide-react-native"`.
- **Аудио, видео и геолокация — запрещены без исключений.** Не разблокировать
  `RECORD_AUDIO`, `CAMERA` под видео, `ACCESS_FINE_LOCATION`/
  `ACCESS_COARSE_LOCATION`/`ACCESS_BACKGROUND_LOCATION` в
  `app.json` `blockedPermissions`, даже если тема приложения формально
  подсказывает такую фичу — искать локальную альтернативу. Единственное
  исключение — **фото**: камеру/галерею можно разблокировать, только если это
  реально нужно, и запрос обязан идти через явное действие пользователя
  (кнопка вроде "Add photo"), не тихо при старте приложения.
- **Палитра — профессиональная, преимущественно светлая.** Приглушённые,
  некрикливые тона. **Тема по умолчанию — всегда light**, `useTheme()` в
  шаблоне больше не следует за системной тёмной темой устройства (раньше
  следовала — и приложение молча становилось тёмным на любом телефоне с
  системным dark mode, хотя просили светлое). Тёмная палитра в `colors.ts`
  остаётся — если "иногда" (см. ниже) добавляешь ручной переключатель тем.
  **Не зацикливаться на "ещё один приглушённый сине/зелёный/фиолетовый"** —
  `docs/PALETTES.md` даёт готовый банк непохожих друг на друга исходных
  наборов тонов (пастель, неон, тёплые винтажные, холодные технологичные и
  т.д.) как сырьё для акцента/hero-градиента/категориальных цветов, если
  выбирать акцент с нуля каждый раз лень или он опять тянется в ту же
  сторону. Банк не отменяет сверку с `DESIGN_REGISTRY.md` ниже — он только
  расширяет, из какого настроения выбирать, а не решает конфликт с
  портфелем сам.
- **Перед вёрсткой экранов — референс, но выбранный СЛУЧАЙНО, не по теме
  напрямую.** Приложений в портфеле 50+, и если каждый раз брать самое
  очевидное тематическое совпадение (кулинарное приложение → референс из
  другого кулинарного приложения), визуал начинает повторяться от app к app.
  Либо спроси пользователя, есть ли референс дизайна, либо (если он говорит
  использовать старые) **выбери случайно** 2-3 `release/creo/*.jpg` из разных
  папок `APPs` — тема референса намеренно НЕ обязана совпадать с темой
  нового приложения, важен только стиль (отступы, типографика, компоновка
  карточек), не тема. Не копировать 1:1 — дизайн всё равно не должен
  повторяться. Внешние источники (Dribbble/Mobbin/collectui.com и подобные
  подборки UI-паттернов) — тоже годится смотреть за композицией
  (расположение кнопок, структура карточек, стиль заголовка), но по тому же
  правилу: подглядывать стиль и композицию, не копировать экран целиком
  вместе с чужим брендингом/иллюстрациями. Заметь: у collectui.com контент
  подгружается через JS, поэтому автоматический просмотр страницы часто не
  видит категории — если нужен конкретный паттерн оттуда, открой его вручную
  в браузере и опиши/перешли, что взять за основу.
- **Расположение элементов на экране — тоже выбирается случайно, не по
  умолчанию.** Сейчас почти все приложения портфеля используют один и тот
  же силуэт: `ScreenHeader` заголовком сверху, длинный вертикальный скролл,
  FAB снизу-справа для "Add". Это тоже начинает повторяться от app к app не
  меньше, чем одинаковая палитра. Перед вёрсткой экранов выбери (случайно
  или по смыслу темы, но не "как в прошлый раз") один **layout-архетип** —
  сочетание навигации, места основного действия и композиции контента,
  внутренне согласованное, а не вперемешку разные оси по отдельности:
  1. **Tab Dashboard** — нижний таб-бар (Home/Stats/Settings), компактный
     фиксированный хедер, на Home — мозаика из 2-колоночных карточек, а не
     один длинный список.
  2. **Single Scroll + FAB** — без таб-бара, один root-стек, всё через один
     длинный скролл с секциями, плавающий круглый FAB снизу-справа для
     основного действия, крупный заголовок, сжимающийся при скролле.
  3. **Segmented Pills Top** — верхний сегмент-контрол вместо таб-бара
     переключает секции на одном экране (как Water/Weight/HIIT у Apexify),
     основное действие — прилипающая внизу кнопка на всю ширину, не FAB.
  4. **Hero Card First** — первым делом крупная hero-карточка с сигнатурным
     виджетом, кнопка основного действия — внутри/под hero-карточкой, а не
     в хедере и не FAB; остальной контент — списком ниже.
  5. **List-first со свайпами** — главный экран — это в первую очередь
     список/таблица записей (swipe-to-delete/edit, как у FridgeChef),
     добавление — тонкая инлайн-строка "+ Add item" в начале/конце списка,
     не плавающая кнопка.
  6. **Rail + Sections** — горизонтальная прокручиваемая лента
     карточек/дат сверху (как CollisionStrip/GiftIdeas), основной контент —
     вертикальными секциями ниже, действие — небольшая pill-кнопка рядом с
     заголовком ленты, не гигантский FAB.
  7. **Minimal No-Header** — без отдельного `ScreenHeader`-заголовка,
     название вшито в первый блок контента, сверху — только компактная
     иконка (настройки/назад), основное действие — вытянутый FAB снизу по
     центру с текстовой подписью.
  8. **Grid Dashboard** — сам Home — это 2-колоночная сетка карточек (не
     список и не один скролл секциями), тап открывает деталь/модалку,
     добавление — отдельная карточка-плейсхолдер "+" в той же сетке.
  9. **Timeline Feed** — вертикальная лента записей по времени (как в
     мессенджере), с разделителями-датами между группами; добавление —
     небольшая кнопка рядом с разделителем "Today", а не FAB поверх всей
     ленты.
  10. **Split Header/Body Card** — верх экрана — фиксированный цветной/
      градиентный блок (приветствие/hero-статистика), низ — белая
      "простыня" с закруглёнными верхними углами, которая скроллится
      поверх нижней части hero-блока (финансовый app-паттерн).
  11. **Wizard/Stepper Flow** — вместо модалки на один экран, основной
      сценарий ввода — многошаговая форма с точками/прогресс-баром
      шагов сверху; подходит темам с составным вводом (несколько полей
      подряд, не одна короткая форма).
  12. **Command Bar Bottom** — внизу закреплена не одна FAB-кнопка, а
      панель на 2-3 быстрых действия (иконка+подпись), между которыми
      реально есть выбор, а не только "Add".
  13. **Sidebar Categories** — узкая колонка категорий/фильтров слева
      (или выезжающая панель), контент — справа; подходит темам с явно
      выраженными категориями/секциями.
  14. **Calendar-first** — главный экран — календарная сетка/неделя,
      записи привязаны к дате; добавление — тап по дню открывает форму
      с этой датой уже подставленной, отдельного FAB нет.
  15. **Chat/Log Console** — вертикальный лог записей снизу вверх,
      ввод — закреплённая внизу строка (как в мессенджере), без
      отдельной модалки добавления вообще.
  16. **Focus Single-Card** — на экране одновременно виден только один
      "текущий" элемент крупной карточкой по центру, переключение между
      элементами/днями — горизонтальным свайпом, а не список/грид.
  Не использовать тот же архетип, что был в последних 3-4 приложениях
  портфеля — сверяться по тому же принципу, что и с палитрой (см. правило
  ниже про `DESIGN_REGISTRY.md`).

  Этот список — не потолок вариативности сам по себе (комбинаций "хорошо
  скомпонованного" экрана объективно не бесконечно много), поэтому силуэт —
  не единственная ось. Дополнительно, независимо от выбранного архетипа,
  можно осознанно варьировать:
  - **Стиль хедера** — крупный заголовок, сжимающийся при скролле / компактный
    фиксированный бар / градиентный-иллюстрированный hero-блок / заголовок
    вшит в первую карточку контента без отдельного хедера вообще.
  - **Структура Stats-экрана** — секции друг под другом одним скроллом /
    табы-переключатели по метрикам / горизонтальный swipe-карусель отдельных
    "отчёт"-карточек.
  - **Стиль пустых состояний** — крупная иллюстрация по центру / компактный
    текст+иконка / карточка-чеклист "с чего начать" вместо обычного EmptyState.
  - **Структура Settings** — сгруппированный список секций (iOS-style) /
    одна карточка с переключателями без группировки / сетка иконок-разделов.
  Комбинация "архетип + 1-2 таких оси, которые реально отличаются от
  последних приложений" — уже достаточно, чтобы не гнаться за придумыванием
  ещё десятков новых базовых силуэтов с нуля.
- **"Добавить запись" — модалка/шторка, а не тихая инлайн-форма.** Пользователь
  ожидает, что нажатие кнопки "Add" открывает форму добавления, а не что
  где-то на экране уже стоит инлайн-форма, которая просто отправляется по
  нажатию. Используй `Modal` (или bottom sheet) с триггером — кнопкой/FAB.
- **Если ввод повторяющийся и структурный (типы дел, продукты, категории) —
  добавь пресеты.** Список готовых значений, которые можно выбрать в один тап
  вместо того чтобы печатать каждый раз — это резко ускоряет реальное
  использование приложения.
- **Обязательный дополнительный экран Stats с красивыми графиками, минимум 4
  отдельные секции** — не один график на весь экран. Ориентир по составу
  (см. `DESIGN_REGISTRY.md` в корне `APPs/`, раздел "Эталон качества"):
  1-2 stat-карточки сверху (стрик/итог/среднее) → один trend-график
  (`BarChart`, за неделю/7-30 дней) → один distribution-график (`DonutChart`,
  разбивка по категориям/статусам) → `Heatmap` (активность по дням) или
  best/worst-каллаут. Используй `DonutChart`/`BarChart`/`AnimatedRing`/
  `Heatmap` из `src/components/` — не изобретай чарты с нуля каждый раз, они
  уже анимированные (см. правило про анимации ниже).
- **Анимации — обязательный минимум, не опциональная полировка.** Ориентир
  качества — Apexify/Standy/FridgeChef/Planti/DreamLog (полный разбор в
  `DESIGN_REGISTRY.md`). На каждый новый экран:
  - **Press-фидбек** — любая нажимаемая карточка/строка (не только кнопки)
    оборачивается в `PressableScale` (`src/components/PressableScale.tsx`),
    не голый `Pressable` с ручным `opacity`.
  - **Стаггер-вход списков/карточек** — при рендере списка или набора
    карточек оборачивать элементы в `Animated.View` с
    `entering={FadeInDown.delay(staggerDelay(index)).duration(400)}`
    (`staggerDelay` — из `src/theme/motion.ts`), а не показывать всё разом.
  - **Один "hero"-анимированный элемент** на главном экране — `AnimatedRing`
    (прогресс/стрик) или `AnimatedCounter` (накрутка числа), не просто
    статичный текст с цифрой.
  - **Payoff на завершение ключевого действия** (сохранил запись/закрыл
    задачу/отметил выполненным) — `SuccessBurst`
    (`src/components/SuccessBurst.tsx`), не просто toast/alert.
  - Тайминги/spring-конфиги брать из `src/theme/motion.ts`
    (`duration`/`easing`/`spring`/`staggerDelay`) — не подбирать магические
    числа заново в каждом компоненте.
- **Планка сложности (05.10.2026, прямая просьба пользователя): приложение
  должно быть замудрённым и по функционалу, и по интерфейсу.** Проверяй себя
  по этому списку перед тем, как звать человека смотреть:
  - связка из 2-3 модулей в `src/lib`, где выход одного — вход другого, а не
    один калькулятор;
  - хотя бы одна сущность с НАКАПЛИВАЕМЫМ состоянием (обновляется от действия
    к действию, а не пересчитывается с нуля);
  - режим "что если" со сравнением до/после, а не просто новым числом;
  - экран/шторка "почему так" — разложенные слагаемые решения движка;
  - движок умеет сказать "так нельзя, вот почему" и дать ранжированные
    альтернативы;
  - 6 экранов, среди них master-detail (отдельный экран детали, не модалка);
  - минимум 3 своих виджета поверх шаблонных, хотя бы один — жестовый
    (drag/pan/long-press/тап по сегменту), а не только анимированный;
  - плотный UI: живой поиск/фильтр, свайп или long-press контекстное меню,
    инлайн-редактирование, липкие заголовки;
  - Stats: 6+ секций, минимум одна интерактивная (тап по сегменту
    перестраивает остальной экран под этот срез).
  Полная формулировка — в `AUTOMATION.md`, раздел действующих правил.
- **Игры не делаем** — если тема, с которой начали разработку, оказалась
  игрой, остановиться и уточнить у пользователя, а не продолжать (визуал в
  играх — не сильная сторона процесса, см. `AUTOMATION.md`).
- **Приложение не должно пересекаться визуально с другими в портфеле.**
  Перед тем как зафиксировать палитру в `src/theme/colors.ts` — свериться с
  `E:\Programering\APPs\DESIGN_REGISTRY.md`: не тот же оттенок акцента и не
  тот же сигнатурный виджет/состав графиков, что в последних 8-10 добавленных
  туда приложениях, и не тот же layout-архетип (см. список выше), что в
  последних 3-4. После того как палитра и Stats-экран готовы — добавить свою
  строку в реестр, **указав в ней и выбранный layout-архетип по имени** (и
  дополнительные оси, если применял — стиль хедера/Stats/EmptyState/Settings)
  — это часть алгоритма разработки, не отдельная задача.
- **Иногда (не обязательно каждый раз) добавляй ручной переключатель тем**
  (light/dark/system) в Settings — особенно если тема приложения выигрывает
  от возможности переключения. Храни выбор в `src/data/settings.ts` и
  передавай как параметр в `useTheme(scheme)`, по умолчанию `"light"`.
  **Если добавляешь этот переключатель** — заведи `useAppTheme()` (кэш выбора
  в zustand `src/store/uiStore.ts` поверх `useTheme()`, см. CycleCalm/MoodPin)
  и **перепиши на него все `src/components/*`, которые сейчас зовут голый
  `useTheme()`** (`Card`, `PrimaryButton`, `SecondaryButton`, `ScreenHeader`,
  `EmptyState`, `Toggle`, `BarChart`, `SuccessBurst`) — иначе экраны уйдут в
  тёмную тему, а переиспользуемые компоненты останутся на светной (проверено
  на CycleCalm и MoodPin: ровно так дизайн и "ломался" в тёмном режиме).
  Заодно проверь `Toggle`: его `thumbColor` не должен быть завязан на
  `theme.colors.onAccent`, если тот в тёмной палитре тёмный, — ползунок
  сольётся с треком, лучше фиксированный светлый цвет.

## Алгоритм разработки

1. Если ещё не переименовано — выполнить
   `node tools/rename-project.js "<App Name>" <slug> com.<slug>.app`.
2. Дизайн-референс (см. правило выше) и выбор layout-архетипа (см. список
   архетипов выше) — до того, как выбирать палитру и вёрстку.
3. Прочитать/дописать `PLAN.md` (создан из `docs/PLAN.template.md` при
   переименовании): архитектурные решения, модель данных, список экранов —
   всё на английском, кроме служебных пометок. Держать 4-6 экранов, **один из
   них — обязательно Stats** (см. правило выше) — шире, значит это v2.
4. Выбрать палитру в `src/theme/colors.ts` — светлую, профессиональную,
   **не такую же, как в других приложениях этого портфеля** — можно
   оттолкнуться от `docs/PALETTES.md`, но свериться с `DESIGN_REGISTRY.md`
   (см. правило выше) до того, как зафиксировать акцент. Обновить константы
   ACCENT/SECONDARY/BACKGROUND в `tools/generate-icons.js` под ту же палитру
   и прогнать `npm run icons`.
5. Заменить `src/data/items.example.ts` на реальные таблицы/запросы,
   `src/db/migrations.ts` — на реальную схему.
6. Экраны в `app/` (expo-router) поверх компонентов из `src/components/`,
   иконки — из `lucide-react-native`, весь видимый текст — на английском.
7. Уведомления (`src/services/notifications.ts`) и haptics
   (`src/services/haptics.ts`) — подключать только если это по смыслу нужно
   приложению. Если не нужны — удалить связанный UI/пермишены, не оставлять
   мёртвый код "на всякий случай".
8. Если логика достаточно сложная (движок игры, подсчёт статистики,
   планировщик) — вынести в чистые функции без React и покрыть юнит-тестами.
9. Пустые состояния (`EmptyState`) везде, где список/статистика может быть
   пустой. Никаких сгенерированных демо-записей вместо реальных данных.
10. Добавить строку в `DESIGN_REGISTRY.md` (акцент, оттенок, сигнатурный
    виджет Stats, **layout-архетип**) — после того как палитра и Stats-экран
    зафиксированы.
11. Запустить `npm run verify` (tsc + тесты + check-rules + expo export). Все
    шаги должны быть зелёными. Если что-то падает — чинить, а не игнорировать.
12. Создать `release/` и `release/creo/` в корне проекта (уже в `.gitignore`
    шаблона), если их ещё нет. Поднять эмулятор (см. `AUTOMATION.md`, раздел
    3), собрать и поставить дев-клиент (`npx expo run:android`), пройтись по
    всем экранам (ничего не падает, нет пустых экранов там, где должны быть
    данные), снять **5-7 скриншотов** (`adb shell screencap`) и сохранить в
    `release/creo/` (`1.png`, `2.png`, ...) — не по одному на экран, а на
    каждый ключевой экран плюс заполненные/интересные состояния (форма
    добавления открыта, сигнатурный виджет с данными, любое второе состояние,
    показывающее механику приложения). Это смоук-проверка, не замена ручной —
    не судит "едет/лагает" ли анимация вживую.
13. Остановиться здесь и явно сообщить: "готово к ручной проверке, скриншоты
    уже в release/creo/" — финальную визуальную проверку через Expo Go на
    реальном телефоне делает пользователь, это отдельный шаг (см.
    AUTOMATION.md в корне `APPs/`), не часть этого алгоритма.

## Жёсткие правила

- Не добавлять бэкенд/сетевые вызовы "про запас".
- Не запрашивать разрешения, которых нет в `app.json` `blockedPermissions`
  ровно потому что их пришлось оттуда убрать и обосновать в `PLAN.md`.
- Не оставлять `console.log`, TODO, моковые данные — `npm run check-rules`
  должен быть зелёным.
- Не копировать дизайн (палитру/компоновку/анимации) один в один с другим
  приложением портфеля, даже если тема та же.
- Никакого текста в UI не на английском, никаких эмодзи вместо иконок,
  никакого личного имени/ника в package name.
- Не оставлять "тихие" инлайн-формы добавления без чёткого триггера
  (кнопка/FAB → модалка) — пользователь должен видеть, что форма открылась.
- Не пропускать экран Stats — это часть обязательного набора экранов, не
  опциональное дополнение. Меньше 4 секций на нём — недоделанный экран.
- Не оставлять кнопки/карточки/списки без анимации (press-фидбек через
  `PressableScale`, стаггер-вход через `staggerDelay`) — статичный UI без
  этого не проходит проверку качества (см. правило про анимации выше).
- Не фиксировать палитру без сверки с `DESIGN_REGISTRY.md` — визуальное
  совпадение с другим приложением портфеля недопустимо, даже при разных темах.
- Не брать дефолтный силуэт "хедер сверху + один длинный скролл + FAB
  снизу-справа" по умолчанию — выбрать layout-архетип из списка (см. правило
  выше), другой, чем в последних 3-4 приложениях портфеля.
